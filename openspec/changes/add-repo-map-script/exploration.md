## Approaches (imports / exports / signatures, no AI, no deps)

| Approach                                                 | Pros                                              | Cons                                                      | Effort |
| -------------------------------------------------------- | ------------------------------------------------- | --------------------------------------------------------- | ------ |
| A. Pure-Node heuristic scanner (regex + small tokenizer) | Zero deps, deterministic, extensible per language | Approximate signatures, edge cases                        | Medium |
| B. TypeScript compiler API (syntax-only)                 | Accurate for JS/TS                                | Needs project-local `typescript`; API drift; TS-only      | Medium |
| C. B when available, else A                              | Best accuracy                                     | Two paths; output differs per machine, breaks determinism | High   |
| D. Bundle typescript / tree-sitter                       | Accurate                                          | Violates no-deps policy                                   | Reject |
| E. Shell out to tsc/knip/madge/ctags                     | Reuses tools                                      | New tool deps, no unified graph                           | Reject |

`node:module.stripTypeScriptTypes` only strips types; it yields no export/signature info.

## Recommendation

Approach A for v1 over `.ts .tsx .mts .cts .js .jsx .mjs .cjs`, behind a per-language extractor table (room for #290/#291/#292 and other languages). C is a follow-up if fidelity becomes a complaint. List files with `git ls-files` in a git repo (honors `.gitignore`), else walk with a built-in ignore list. POSIX paths, no timestamp. Stack and conventions detection are plain file checks. Layout: `index.mjs` plus helpers (walk, stack, extract, graph, render). JSON envelope `shitaku.catalog.repo-map/v1`: `{commit, tree, stack, entryPoints, modules[{path, imports, exports[{name,kind,signature}]}], graph, conventions}`; Markdown is a pure function of the JSON.

## Open product decisions

1. Output location and write mode (`.shitaku/repo-map.{json,md}`, stdout, `--out`); gitignored or committed; how #226 finds it.
2. Determinism: omit `generatedAt` (recommended); `commit` value when git is missing or tree is dirty.
3. Language scope for v1 (JS/TS only vs. Python/Go/others).
4. Markdown size cap and truncation (is JSON complete while Markdown truncates?).
5. Monorepos/workspaces.
6. Tree granularity (file vs. directory as "module").
7. Exit codes (meaningful exit 1, e.g. `--check` for stale map).
8. Flags (`--format`, `--out`, `--max-depth`, `--ignore`).
9. Command detection sources (`package.json` only vs. Makefile/Cargo).

## Risks

- `bundled-catalog.test.ts` hard asserts.
- Hand-written prose goes stale; CI `docs:catalog:check` fails if the README table is not regenerated.
- Heuristic parse accuracy: template/regex literals, `export *`, barrels, `@/` aliases, tsconfig `paths`, package `exports`. Needs explicit `unresolved` handling and tricky-case fixtures.
- Large repos need size/count guards; git may be missing (`commit: null`); Windows paths need POSIX normalization.
- 400-line review budget likely exceeded. Possible split: slice 1 scanner + stack + JSON; slice 2 Markdown + registration + docs. Delivery is `ask-on-risk`: confirm chain strategy at proposal time.
- Strict TDD is on: tests and fixtures first per helper.
