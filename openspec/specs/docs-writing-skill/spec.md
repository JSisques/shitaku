# docs-writing-skill Specification

## Purpose

Catalog-bundled **docs-writing** skill: single generic English skill that guides an agent to write and maintain project documentation (README, CHANGELOG, code comments and JSDoc/TSDoc, docs kept in sync with code, concise neutral tone). Model-invocable, installable via existing skills-install. Scope is documentation only; PR titles and bodies belong to `pr-writing`.

## ADDED Requirements

### Requirement: Bundled registration and valid frontmatter

The bundled catalog MUST list `docs-writing` in `items.skills` and MUST ship `catalog/skills/docs-writing/SKILL.md` with YAML frontmatter: single-line `name` equal to `docs-writing` and single-line, single-quoted `description` of at most 250 characters, starting with `Trigger:`, containing no quotes or pipes. The skill MUST load and validate under existing catalog rules.

#### Scenario: Bundled load succeeds

- GIVEN the default bundled catalog after this change
- WHEN the catalog is loaded
- THEN skill `docs-writing` is available and valid
- AND frontmatter `name` equals the skill directory name
- AND the bundled skill list is `docs-writing`, `example-skill`, `pr-writing`, `socratic-method`
- AND the `docs-writing` entry has `files: ['SKILL.md']`

#### Scenario: Frontmatter rejects empty or mismatched identity

- GIVEN frontmatter missing `description`, or `name` not equal to `docs-writing`
- WHEN the catalog is loaded
- THEN the skill MUST NOT be selectable
- AND the error MUST name the offending path and reason

### Requirement: README guidance

The skill MUST instruct the agent to structure a README with purpose first, then install, usage, configuration, and contributing/license links. When a README already exists, the skill MUST instruct the agent to follow its existing structure instead of the default layout.

#### Scenario: New README

- GIVEN a repository without a README
- WHEN an agent follows `docs-writing` to create one
- THEN the README states purpose first
- AND includes install, usage, configuration, and contributing/license links

#### Scenario: Existing README structure

- GIVEN a repository with an established README layout
- WHEN the agent updates it
- THEN the agent follows the existing structure

### Requirement: CHANGELOG guidance

The skill MUST instruct the agent to follow the Keep a Changelog format and map Conventional Commits to its sections. It MUST forbid hand-editing changelog sections generated by a release tool (for example semantic-release). When releases are automated, the agent MUST change commit messages rather than the changelog file.

#### Scenario: Manually maintained changelog

- GIVEN a repository whose CHANGELOG is maintained by hand
- WHEN the agent records a change
- THEN the entry follows Keep a Changelog structure and the Conventional Commits mapping

#### Scenario: Release-generated changelog

- GIVEN the CHANGELOG is generated by a release tool
- WHEN the agent is asked to document a change
- THEN it MUST NOT hand-edit the generated sections
- AND it adjusts commit messages instead

### Requirement: Comments and JSDoc/TSDoc guidance

The skill MUST instruct the agent to write comments that explain why, not what, and to document public API contracts (params, returns, throws) with JSDoc/TSDoc. It MUST forbid commented-out code and stale TODOs.

#### Scenario: Comment explains intent

- GIVEN an agent adds a comment to code
- WHEN it writes the comment
- THEN the comment explains why, not what the code does

#### Scenario: Public API documented

- GIVEN a public function or exported API
- WHEN the agent documents it
- THEN the doc comment covers params, returns, and throws

#### Scenario: Dead code and stale TODOs

- GIVEN commented-out code or a stale TODO
- WHEN the agent touches that area
- THEN it MUST NOT add commented-out code or stale TODOs

### Requirement: Docs kept in sync with code

The skill MUST instruct the agent to update documentation in the same change as the behavior it describes. When the repository has a docs generator or check script, the agent MUST run it and MUST NOT hand-edit its generated output.

#### Scenario: Behavior change updates docs

- GIVEN a change alters documented behavior
- WHEN the agent implements it
- THEN the related documentation is updated in the same change

#### Scenario: Docs generator present

- GIVEN the repository has a docs generator and check script
- WHEN the agent updates generated documentation
- THEN it runs the generator and check
- AND MUST NOT hand-edit the generated output

### Requirement: Tone and style

The skill MUST instruct the agent to write concise, neutral documentation in second person or imperative voice, and to follow the existing repository style, language, style guide, or template when present.

#### Scenario: Existing style guide or template

- GIVEN the repository provides a style guide or documentation template
- WHEN the agent writes documentation
- THEN it follows that guide or template

#### Scenario: Default tone

- GIVEN no style guide exists
- WHEN the agent writes documentation
- THEN the text is concise and neutral, in second person or imperative voice

### Requirement: Scope limited to documentation

The skill MUST state that it is not for pull request titles or descriptions, or commit messages. It MUST NOT cover agent instruction files (for example AGENTS.md conventions) or release notes authored by a release tool. `catalog/skills/pr-writing/SKILL.md` MUST remain unchanged.

#### Scenario: Out-of-scope content absent

- GIVEN `catalog/skills/docs-writing/SKILL.md` after the change
- WHEN its content is inspected
- THEN it excludes PR titles and descriptions and commit messages
- AND does not instruct authoring agent instruction files or tool-generated release notes

#### Scenario: pr-writing unchanged

- GIVEN this change is applied
- WHEN the authored diff is reviewed
- THEN `catalog/skills/pr-writing/SKILL.md` is unchanged

### Requirement: Generic and model-invocable

The skill MUST be generic (usable in any repository) and written in concise English. Frontmatter MUST NOT set `disable-model-invocation: true` (the key SHOULD be omitted). Its decision gates MUST cover: release-generated changelog (do not edit), existing docs generator (run it), existing style guide or template (follow it).

#### Scenario: Invocable and generic

- GIVEN `catalog/skills/docs-writing/SKILL.md` after the change
- WHEN frontmatter and body are inspected
- THEN `disable-model-invocation` is absent or not `true`
- AND no shitaku-specific file, tool, or convention names are hardcoded

### Requirement: Installable create when absent

When the target is absent, `init --skills docs-writing --dry-run` MUST classify `create` and MUST NOT write files, backups, or manifest. Applied install MUST be byte-identical under existing skills-install (referenced; MUST NOT amend that domain).

#### Scenario: Dry-run create when absent

- GIVEN no target directory for `docs-writing`
- WHEN `init --skills docs-writing --dry-run` runs
- THEN the plan classifies `docs-writing` as `create`
- AND no file, backup, or manifest changes occur

#### Scenario: Byte-identical install under existing skills-install

- GIVEN the bundled `docs-writing` skill and an absent target
- WHEN `init --skills docs-writing` applies successfully
- THEN the target skill tree is byte-identical to the catalog skill
- AND behavior follows existing skills-install requirements without modification

### Requirement: Catalog-only surface with synced docs

Delivery MUST be catalog data, tests, and regenerated docs only. `src/` hexagonal layers MUST NOT change. The README skills table and website catalog pages (en, es) MUST be regenerated so the docs check scripts pass.

#### Scenario: No src changes

- GIVEN this change is applied
- WHEN the authored diff is reviewed
- THEN `src/` is unchanged
- AND no install-time templating is introduced

#### Scenario: Generated docs in sync

- GIVEN `docs-writing` is registered in the catalog
- WHEN `docs:catalog:check` and the website catalog check run
- THEN both pass
- AND README and website en/es list `docs-writing`
