## Activation Contract

Use when asked to write, update, or review project documentation: README, CHANGELOG, code comments, JSDoc/TSDoc, or other docs that describe behavior. Not for pull request titles or descriptions, commit messages, or agent instruction files.

## Hard Rules

- Inspect existing docs and conventions before writing. Follow the existing structure, style guide, templates, and language.
- README: lead with the purpose, then install, usage, configuration, and links to contributing and license. Keep the existing section order when one exists.
- CHANGELOG: use Keep a Changelog format and map Conventional Commits to its categories. Never hand-edit sections generated by a release tool (for example semantic-release); change the commit messages instead.
- Comments explain why, not what. Document public API contracts with JSDoc/TSDoc (params, returns, throws). Leave no commented-out code and no stale TODOs.
- Update docs in the same change as the behavior they describe. Run the docs generators and their check scripts; never hand-edit generated output.
- Write concise, neutral prose in second person or imperative. Do not pad, and do not market.
- Stay generic: do not assume any repository-specific file, tool, label, or convention name.

## Decision Gates

| Condition                                  | Action                                                                          |
| ------------------------------------------ | ------------------------------------------------------------------------------- |
| CHANGELOG generated by a release tool      | Do not edit it; make commit messages carry the change, and say so               |
| CHANGELOG maintained by hand               | Add entries under Unreleased using Keep a Changelog categories                  |
| Repository has a docs generator            | Run it and its check script; never hand-edit generated output                   |
| Repository has a style guide or template   | Follow it over the defaults in this skill                                       |
| No README, or README missing core sections | Use purpose, install, usage, configuration, then contributing and license links |
| Public API changed                         | Update its JSDoc/TSDoc (params, returns, throws) in the same change             |
| Docs language differs from English         | Write in the existing docs language and register                                |

## Execution Steps

1. Identify what changed and which docs describe it (`git diff`, the task, the user statement).
2. Inspect the README layout, the CHANGELOG origin and release config, docs generators and their check scripts, and any style guide or templates.
3. Update the README sections the change affects; add missing core sections only when the README lacks them.
4. Update the CHANGELOG only when it is hand-maintained: add entries under Unreleased. Map `feat` to Added, `fix` to Fixed, removals to Removed, deprecations to Deprecated, security fixes to Security, and other user-visible changes to Changed. Omit `chore`, `test`, `ci`, `build`, `style`, and `refactor` unless user visible.
5. Add or fix comments and JSDoc/TSDoc on touched public API, explaining why rather than restating the code.
6. Run the docs generators and check scripts found in step 2, and fix any drift they report.
7. Present the changes and any documentation gaps that remain.

## Output Contract

Return the edited or proposed docs, a list of files changed, the generators or checks run with their results, and anything skipped with the reason (for example a release-generated CHANGELOG) or still out of sync.
